# M3CAP-yoke-v1 容量对照报告

yoke/rust、5N5A、固定 P1 候选下的双库容量对照（R0/RN/RF/RNF）。全部结果**探索性**：查询集复用、k 为裁剪预算非独立源帧数、源身份未知、查询已用于研究决策。

## 1. 冻结与固定候选（归因关键）
- 数据与模型完全复用 M3BENCH：N5 名单、k5 seed0-2 故障支持、query_k5、YOLO 权重、mapper_B、预处理与 L2；全部 SHA256 见 FROZEN_INPUTS.json
- 先固定候选：每参照组 N256（原流程 FPS256）**同时作为 P1 筛选参照**；每种子故障 8000 patch 按 N256 稳定排序取前 50% = **4000 候选**，索引与 SHA256 存 P1_CANDIDATES.json；四臂共享候选，未因大库重筛
- F256 与历史 p1_fault_bank 逐元素一致（15/15 配置 allclose=True）；容量=min(上限,候选数)，F 大臂实际 4000（<4096，全保留未跑 FPS），无重复向量凑容量
- FPS 前缀说明：实现返回 sorted(chosen)，列表前缀不等是排序伪影；贪心选择顺序与 cap 无关，**集合级包含验证 5/5 成立**（N4096 ⊇ N256，F4096 ⊇ F256），数值不变量有意义

## 2. 复现与正确性
- **R0 全部 15 配置与 M3BENCH Ours g2 逐图分数 max|diff| = 0.00e+00**（门限 1e-4，未放宽）
- PatchCore 复用历史 yoke g2 5 个 10N 配置重算 AUROC：均值 **0.834854**，与简报预期完全一致；查询路径集合核对一致
- 分块最大相似度 vs 直接计算 max diff = 0.0；eval/no_grad，mapper 前后哈希一致；分数有限方向正确
- 数值不变量：sN(4096) ≥ sN(256)、sF(4000) ≥ sF(256) 逐 patch 成立；仅扩 N 分数不增、仅扩 F 分数不减

## 4. 六问回答
1. **正常库扩大是否改善？否。** RN 均值 −0.030，11/15 配置为负；正常侧匹配分虽升高（不变量验证），但双库差值被压缩，排序变差。
2. **故障库扩大是否改善？是，且是唯一的正收益方向。** RF +0.071，全部 5 参照组为正（14/15 配置为正，唯一负值 ref3005 seed1 = −0.014）。
3. **同时扩大有无额外收益？没有。** RNF −0.003 ≈ RF(+0.071) 与 RN(−0.030) 的代数和，N 扩容的损失抵消 F 扩容的收益，无正向交互。
4. **与 PatchCore 差距：从 −0.184 缩小到 −0.113**（RF 臂；RNF −0.188 未缩小）。即便最有利容量配置仍落后 PatchCore 10N 约 11 个点，且未排除 1536 维 WRN 特征差异。
5. **跨参照组/种子保持？** RF 的方向在 5/5 参照组保持，但幅度波动大（ref3004 +0.172 vs ref3003 +0.041），种子间有个别翻转；RN/RNF 方向不稳定。
6. **每存储换多少 AUROC？** F 库 256→4000 原型（128 维 FP32，+1.953125 MiB）→ +0.071；N 库 256→4096（+2.0 MiB）→ −0.030；双扩 +3.703125 MiB → −0.003。容量限制主要在**故障库一侧**。

## 5. 资源成本
- 推理常驻库（128 维 FP32，字节数与 BANK_MANIFEST/RESOURCE_COST.json 一致）：R0 0.250 MiB → RN 2.125 MiB → RF 2.078125 MiB → RNF 3.953125 MiB
- 构建期 P1 参照（N256，每参照组一次）与推理期常驻库分开统计；建库+缓存评分全程 wall 15.6s，峰值显存 0.45GB；吞吐探针外推 31.5s ≪ 1 GPU 时预算
- 本轮为缓存评分耗时，**不称为完整推理延迟**；不引用历史 55–164 倍速比

## 6. 解释边界
- 大库提高最大匹配分不保证正常/故障排序更好——RN 正是反例
- 扩 F 有效支持“原 256 容量造成故障侧限制”；扩 N 无效**不能**宣布 YOLO 无效，但降低了继续扩正常库的优先级
- 不自动追加更大容量、换主干、NVE 或其他类别；Ours 5N5A vs PatchCore 10N 非同监督组成对照
- 不根据查询成绩挑最佳配置作为正式结果；以上均为逐配置完整披露后的汇总
